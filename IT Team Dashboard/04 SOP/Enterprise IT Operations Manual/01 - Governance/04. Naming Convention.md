# Naming Convention — Chuẩn đặt tên hạ tầng hoàn chỉnh

Liên quan: [[../04 - Active Directory/Tiered Administration Project/01. Phase 1 - Admin Account Standardization]] · [[../04 - Active Directory/Tiered Administration Project/03. Phase 3 - Security Groups (AGDLP)]] · [[../04 - Active Directory/Tiered Administration Project/02. Phase 2 - OU Design]]

## 1. Mục đích
Chuẩn hóa tên gọi cho **toàn bộ đối tượng hạ tầng** (Server, VM, PC, Laptop, thiết bị mạng, máy in...) — đảm bảo dễ đọc, dễ tra cứu, dễ mở rộng, và tương thích giới hạn kỹ thuật của Windows (NetBIOS name).

## 2. Phạm vi áp dụng
Server vật lý, Server ảo (VM), Workstation, Laptop, Thin Client, Switch, Firewall, Access Point, Máy in, và tài khoản/nhóm AD (tham chiếu chuẩn đã có tại Phase 1/3 của dự án AD).

## 3. Quyết định thiết kế — Vì sao chọn mô hình này

### 3.1. Bỏ `<Tier>` ra khỏi tên Server, dùng `<Environment>` thay thế
Anh đề xuất 2 phiên bản: `<Location>-<Tier>-<Role>-<ID>` và `<Site>-<Environment>-<Role>-<Sequence>`. Em khuyến nghị chốt theo phiên bản thứ 2, lý do:
- **Tier (0/1/2)** là khái niệm **bảo mật quản trị** (ai được đăng nhập vào máy nào) — đã được kiểm soát qua **OU placement** trong dự án Tiered Administration (`OU=Tier0-DC`, `OU=Tier1-AppServers`), không cần lặp lại trong hostname.
- Nếu nhét Tier vào tên máy, khi tổ chức lại mô hình Tier (ví dụ nâng SQL từ Tier 1 lên coi như Tier 0 vì độ nhạy cảm dữ liệu), sẽ phải **đổi tên server** — rất tốn kém (ảnh hưởng DNS, SPN, Kerberos, cấu hình ứng dụng, chứng chỉ SSL...).
- **Environment (PRD/DEV/UAT/LAB/DR)** ổn định hơn nhiều theo thời gian và là thông tin vận hành thực sự cần thấy ngay trên tên máy (tránh nhầm xóa nhầm server Production).

**→ Chuẩn chốt cho Server/VM:**
```
<Site>-<Environment>-<Role>-<Sequence>
```

### 3.2. ⚠️ Cảnh báo giới hạn kỹ thuật: NetBIOS hostname ≤ 15 ký tự
Windows vẫn giới hạn NetBIOS computer name tối đa **15 ký tự** (dù AD hiện đại dùng FQDN là chính, một số thành phần cũ — SQL Named Instance, Print Spooler, ứng dụng legacy — vẫn phụ thuộc NetBIOS name). Với danh sách Site anh đưa, có 2 vấn đề cần sửa trước khi áp dụng:

| Vấn đề | Ví dụ vi phạm | Cách sửa |
|---|---|---|
| Site `Factory1`/`Factory2` quá dài (8 ký tự) → `Factory1-PRD-MES-01` = 20 ký tự, vượt giới hạn | `Factory1-PRD-MES-01` ❌ | Rút gọn còn `FC1`/`FC2` → `FC1-PRD-MES-01` = 14 ký tự ✅ |
| Site `DC1`/`DC2` (Datacenter) **trùng viết tắt** với Role `DC` (Domain Controller) → `DC1-PRD-DC-01` dễ đọc nhầm | `DC1-PRD-DC-01` ⚠️ dễ nhầm | Đổi thành `DTC1`/`DTC2` (Datacenter 1/2) → `DTC1-PRD-DC-01` = 15 ký tự ✅, rõ nghĩa hơn |

**→ Bảng Site chính thức đã điều chỉnh ở mục 4.1 bên dưới.**

### 3.3. Case & ký tự
- Toàn bộ **VIẾT HOA**, phân tách bằng dấu gạch ngang `-` duy nhất (không dùng `_` cho tên máy, khác với tên Group AD dùng `_`).
- Không dùng khoảng trắng, ký tự Unicode có dấu, hoặc ký tự đặc biệt ngoài `-` và `0-9A-Z`.

## 4. Quy trình thực hiện — Bảng chuẩn đầy đủ

### 4.1. Site (đã rút gọn để đảm bảo ≤ 15 ký tự tổng thể)
| Mã Site | Ý nghĩa                                                               |
| ------- | --------------------------------------------------------------------- |
| `HQ`    | Trụ sở chính                                                          |
| `HCM`   | Chi nhánh Hồ Chí Minh                                                 |
| `HN`    | Chi nhánh Hà Nội                                                      |
| `DN`    | Chi nhánh Đà Nẵng                                                     |
| `FTY1`  | Nhà máy 1 (Factory 1)                                                 |
| `FTY2`  | Nhà máy 2 (Factory 2)                                                 |
| `DTC1`  | Datacenter 1 (phòng máy chủ/co-location riêng, nếu tách biệt khỏi HQ) |
| `DTC2`  | Datacenter 2 (DR site hoặc DC dự phòng)                               |

### 4.2. Environment
| Mã | Ý nghĩa |
|---|---|
| `PRD` | Production |
| `DEV` | Development |
| `UAT` | User Acceptance Testing |
| `LAB` | Lab / Thử nghiệm kỹ thuật |
| `DR` | Disaster Recovery |
| `STG` | Staging (tùy chọn — thêm nếu tổ chức có bước staging riêng biệt trước khi lên PRD) |

### 4.3. Role — Server/VM (bảng chuẩn, phân nhóm theo chức năng)

**Hạ tầng lõi (Tier 0)**

| Role | Ý nghĩa |
|---|---|
| `DC` | Domain Controller (mặc định tích hợp sẵn DNS + DHCP nếu chạy trên cùng máy — xem quy tắc 4.6) |
| `CA` | Certificate Authority |
| `DNS` | DNS Server **độc lập**, không tích hợp trên DC |
| `DHCP` | DHCP Server **độc lập**, không tích hợp trên DC |
| `NPS` | Network Policy Server (RADIUS/MFA) |

**Server ứng dụng (Tier 1)**

| Role | Ý nghĩa |
|---|---|
| `SQL` | SQL Server |
| `IIS` | IIS Web Server (tổng quát) |
| `WEB` | Website (nếu tách riêng khỏi IIS role, ví dụ web tĩnh) |
| `API` | API Server |
| `APP` | Application Server (tổng quát) |
| `ERP` | ERP Server |
| `MES` | Manufacturing Execution System |
| `GLPI` | GLPI Server |
| `FS` | File Server |
| `RDS` | Remote Desktop Services |
| `WSUS` | WSUS (Patch Management) |

**Hạ tầng vận hành**

| Role | Ý nghĩa |
|---|---|
| `BKP` | Backup Server |
| `MON` | Monitoring Server (Zabbix/Grafana/PRTG) |
| `LOG` | Syslog/Log Collector |
| `VMH` | Hyper-V Host (vật lý — bản thân Host, không phải VM) |
| `ESX` | VMware ESXi Host (vật lý — bản thân Host, không phải VM) — tách riêng khỏi `VMH` vì khác nền tảng ảo hóa, khác console quản trị (vCenter vs Hyper-V Manager/SCVMM), khác đội kỹ thuật phụ trách |
| `NAS` | Storage/NAS |

**Mở rộng khuyến nghị thêm (không có trong danh sách gốc, nên bổ sung khi cần)**

| Role | Ý nghĩa |
|---|---|
| `SAN` | SAN Storage (nếu tách riêng NAS/SAN) |
| `LB` | Load Balancer |
| `PROXY` | Proxy Server |
| `AV` | Antivirus/EDR Management Server |
| `SIEM` | SIEM Server (nếu tách riêng khỏi MON/LOG) |
| `VPN` | VPN Gateway (nếu là server riêng, không tính Firewall tích hợp VPN) |

### 4.4. Ví dụ áp dụng chuẩn Server/VM
```
HQ-PRD-DC-01          Domain Controller chính tại HQ
HQ-PRD-DC-02          Domain Controller phụ tại HQ
HQ-PRD-SQL-01         SQL Server Production tại HQ
HQ-PRD-GLPI-01        GLPI Server
HQ-PRD-FS-01          File Server
HQ-PRD-VMH-01         Hyper-V Host 1
HQ-PRD-VMH-02         Hyper-V Host 2
HQ-PRD-ESX-01         VMware ESXi Host 1 (Production, HQ)
HQ-PRD-ESX-02         VMware ESXi Host 2
HQ-PRD-ESX-03         VMware ESXi Host 3
HQ-PRD-ESX-04         VMware ESXi Host 4
DTC2-DR-ESX-01        VMware ESXi Host 5 — DR site, dùng cho Disaster Recovery
DTC2-DR-ESX-02        VMware ESXi Host 6 — DR site
HQ-PRD-BKP-01         Backup Server
HQ-PRD-MON-01         Monitoring Server
HQ-DEV-SQL-01         SQL Server môi trường Dev
HQ-UAT-APP-01         Application Server môi trường UAT
FC1-PRD-MES-01        MES Server tại Nhà máy 1
DTC2-DR-DC-01         Domain Controller dự phòng tại Datacenter 2 (DR site)
```

### 4.5. Quy tắc Server đa vai trò (Multi-Role)
Khi 1 server vật lý/VM chạy đồng thời nhiều vai trò (ví dụ vừa là SQL Server vừa host database ERP):

**Nguyên tắc:** đặt tên theo **Role nghiệp vụ chính** (primary business function), **không nhồi 2 Role vào 1 tên** — vai trò phụ ghi chú trong GLPI Asset (trường "Ghi chú"/"Tài liệu đính kèm"), không đưa vào hostname.

| Tình huống | Khuyến nghị |
|---|---|
| Server SQL riêng, không phục vụ ERP cụ thể | `HQ-PRD-SQL-01` |
| Server SQL **chỉ dùng riêng** cho ERP (không dùng chung) | `HQ-PRD-ERPDB-01` (ưu tiên vì phản ánh đúng mục đích kinh doanh) |
| Server chạy chung nhiều DB nghiệp vụ khác nhau (SQL dùng chung) | `HQ-PRD-SQL-01`, ghi rõ trong GLPI database nào đang chạy trên đó |

> Tránh tuyệt đối kiểu đặt tên `HQ-PRD-SQLERPMESAPP-01` — không đọc được, vi phạm giới hạn ký tự, và không mở rộng được khi thêm vai trò thứ 3.

### 4.6. Quy tắc DC tích hợp DNS/DHCP
Trong AD, Domain Controller **mặc định luôn tích hợp sẵn DNS** (AD-integrated DNS) và thường kiêm luôn DHCP ở doanh nghiệp vừa. Quy tắc:
- Nếu DNS/DHCP chạy **trên cùng máy** với Domain Controller → **chỉ đặt tên theo Role `DC`**, không tạo thêm tên `DNS`/`DHCP` riêng cho cùng 1 máy vật lý.
- Role `DNS`/`DHCP` **chỉ dùng** khi triển khai server DNS hoặc DHCP **độc lập, tách riêng khỏi DC** (ví dụ DHCP Server riêng cho mạng Guest/IoT không liên kết AD).

### 4.7. Sequence (số thứ tự)
| Loại đối tượng | Số chữ số | Ví dụ |
|---|---|---|
| Server/VM | 2 chữ số, bắt đầu `01` | `01`, `02`, ... `99` |
| PC/Laptop/Thin Client | 3 chữ số, bắt đầu `001` | `001`, `002` (bắt buộc 3 số vì quy mô hiện tại đã 420 workstation, dễ vượt 99) |
| Switch/AP/Printer | 2 chữ số, bắt đầu `01` | `01`, `02` |

**Quy tắc cấp số:** luôn dùng số **kế tiếp nhỏ nhất chưa dùng** trong cùng nhóm `<Site>-<Environment>-<Role>` (hoặc `<Site>-<Department>-<Type>` với PC) — không tái sử dụng số của thiết bị đã thanh lý trong vòng tối thiểu 12 tháng, tránh nhầm lẫn log lịch sử.

### 4.8. Hyper-V — Host và VM đặt tên độc lập nhau
```
Host:  HQ-PRD-VMH-01, HQ-PRD-VMH-02
VM (đặt tên theo đúng Role của chính VM đó, không liên quan gì đến tên Host):
  HQ-PRD-DC-01
  HQ-PRD-SQL-01
  HQ-PRD-FS-01
  HQ-PRD-GLPI-01
```
> Không đặt tên VM kiểu `HQ-PRD-VMH01-SQL-01` (gắn theo Host) — VM có thể Live Migration sang Host khác bất kỳ lúc nào, gắn tên theo Host ban đầu sẽ gây sai lệch ngay khi di chuyển.

### 4.9. Workstation (PC/Laptop/Thin Client)
```
<Site>-<Department>-<Type>-<Sequence>
```
Không dùng Environment (workstation luôn là "thực tế đang dùng", không có khái niệm Dev/UAT).

**Type:**

| Mã | Ý nghĩa |
|---|---|
| `PC` | Máy tính để bàn |
| `LT` | Laptop |
| `TC` | Thin Client |

**Department:** dùng đúng mã phòng ban đã chuẩn hóa trong AD OU (`IT`, `HR`, `QC`, `QA`, `MFG`, `WH`, `FIN`, `PROD`...) — xem [[../04 - Active Directory/Tiered Administration Project/02. Phase 2 - OU Design]] để đồng bộ 1 bộ mã phòng ban duy nhất dùng chung cho cả OU lẫn tên máy.

**Ví dụ:**
```
HQ-IT-PC-001
HQ-HR-PC-002
HQ-QC-PC-003
FC1-MFG-PC-001
HQ-IT-LT-001
FC1-PROD-TC-001
```

### 4.10. Thiết bị mạng & ngoại vi
| Loại | Chuẩn | Ví dụ |
|---|---|---|
| Switch | `<Site>-SW-<Vai trò>-<Sequence>` | `HQ-SW-CORE-01`, `HQ-SW-ACC-01`, `HQ-SW-ACC-02` |
| Firewall | `<Site>-FW-<Sequence>` | `HQ-FW-01` |
| Access Point | `<Site>-AP-<Sequence>` | `HQ-AP-01`, `HQ-AP-02` |
| Máy in | `<Site>-PRN-<Phòng ban>-<Sequence>` | `HQ-PRN-HR-01`, `HQ-PRN-QA-01`, `HQ-PRN-WH-01` |

**Vai trò Switch:** `CORE` (Core Switch), `ACC` (Access Switch), `DIST` (Distribution Switch, nếu có 3-layer).

### 4.11. Đồng bộ với chuẩn tài khoản/nhóm AD đã có (không thay đổi, chỉ tham chiếu lại)
Chuẩn Server/PC ở trên là **tên thiết bị**, khác với chuẩn **tài khoản/nhóm** đã chốt tại Phase 1 và Phase 3 dự án AD — giữ nguyên, không gộp 2 hệ thống:

| Loại | Chuẩn | Ví dụ |
|---|---|---|
| User thường | `<tên viết tắt>` | `nva` |
| Admin theo Tier | `adm0.*` / `adm1.*` / `adm2.*` | `adm1.nva` |
| Service Account | `svc_<tên hệ thống>` | `svc_glpi`, `svc_sql_gmsa` |
| Global Group | `GG_<Phòng ban/Chức năng>` | `GG_IT_Helpdesk` |
| Domain Local Group | `DL_<Tài nguyên>_<Quyền>` | `DL_FileServer_HR_ReadWrite` |
| GPO | `<Phạm vi>-<Mục đích>` | `Baseline-AllServers-SecuritySettings` |

## 5. Kiểm tra sau triển khai
- [ ] Toàn bộ tên Server/VM ≤ 15 ký tự (kiểm tra bằng công thức: độ dài Site + 1 + độ dài Environment + 1 + độ dài Role + 1 + độ dài Sequence).
- [ ] Không còn xung đột giữa mã Site và mã Role (đã xử lý `DC1/DC2` → `DTC1/DTC2`).
- [ ] Mỗi Site/Environment/Role dùng đúng bảng mã đã chuẩn hóa ở mục 4, không tự sáng tạo mã mới ngoài quy trình mục 7.
- [ ] Đối chiếu tên mới với [[../04 - Active Directory/04. Group Matrix]] và GLPI Asset — không có bản ghi trùng tên.

## 6. Rollback (nếu có)
Đổi tên server đang hoạt động (đặc biệt Domain Controller, SQL Server có Named Instance, hoặc server có chứng chỉ SSL cấp theo tên) là thao tác rủi ro cao — **không đổi tên hàng loạt ngay lập tức**. Quy trình khuyến nghị:
1. Áp dụng chuẩn mới cho **toàn bộ thiết bị mới** ngay từ bây giờ.
2. Với thiết bị hiện có, lên kế hoạch đổi tên dần theo lịch bảo trì định kỳ (đổi tên Server yêu cầu restart, với DC cần quy trình riêng an toàn hơn — xem thêm tài liệu Windows Server module khi được xây dựng).
3. Ghi log việc đổi tên vào [[../04 - Active Directory/07. AD Change Log]].

## 7. Kiểm tra bảo mật
- [ ] Tên Site/Role **không được** để lộ thông tin nhạy cảm ra bên ngoài nếu hostname bị lộ qua DNS public/SSL certificate (ví dụ không đặt tên tiết lộ rõ "đây là server chứa dữ liệu tài chính" theo cách dễ đoán quá mức) — mức độ rủi ro thấp với chuẩn hiện tại nhưng cần lưu ý khi mở rộng Role mới.
- [ ] Danh sách mã Site/Environment/Role chính thức phải được duy trì tập trung (mục 8), tránh tình trạng mỗi kỹ sư tự đặt mã khác nhau gây phân mảnh chuẩn.

## 8. Quy trình quản trị & mở rộng chuẩn (Governance)
- Toàn bộ mã Site/Environment/Role chính thức = bảng tại mục 4 trong file này — đây là **nguồn chuẩn duy nhất (single source of truth)**.
- Khi cần thêm Site mới (mở chi nhánh) hoặc Role mới (triển khai hệ thống mới chưa có trong danh sách): tạo Change Request theo [[../01 - Governance/09. Change Policy]], IT Manager phê duyệt, sau đó **cập nhật ngay bảng tại mục 4** trước khi đặt tên thiết bị đầu tiên theo mã mới.
- Đồng bộ song song vào GLPI: mã Site/Role nên khớp với Dropdown "Location"/"Category" trong GLPI Asset để báo cáo nhất quán giữa 2 hệ thống.
