# AppLocker — Chặn Browser/Outlook/Teams trên tài khoản Admin

Liên quan: [[../04 - Active Directory/Tiered Administration Project/01. Phase 1 - Admin Account Standardization]] · [[../04 - Active Directory/Tiered Administration Project/05. Phase 5 - Tiered Administration]] · [[../04 - Active Directory/Tiered Administration Project/08. Phase 8 - GPO Security Baseline]]

## 1. Mục đích
Hiện thực hóa kỹ thuật quy tắc đã nêu ở [[../04 - Active Directory/Tiered Administration Project/01. Phase 1 - Admin Account Standardization|Phase 1]]: tài khoản Admin (`adm0.*`, `adm1.*`, `adm2.*`) **chỉ dùng cho tác vụ quản trị**, không được dùng để lướt web/check mail. Nếu chỉ dựa vào "ý thức" kỹ sư thì không đủ — cần chặn bằng kỹ thuật. AppLocker cho phép **Deny theo đúng User/Group** (khác Software Restriction Policy chỉ chặn được toàn máy, không phân biệt được ai đang đăng nhập).

## 2. Phạm vi áp dụng
Tài khoản thuộc `GG_Tier0-Admins`, `GG_Tier1-Admins`, `GG_Tier2-Admins` — áp dụng trên mọi máy các tài khoản này có thể đăng nhập (Domain Controller, Server Tier 1, Workstation Tier 2 khi Helpdesk RDP hỗ trợ).

**Ứng dụng bị chặn:** Google Chrome, Microsoft Edge, Mozilla Firefox (toàn bộ trình duyệt — chặn 1 trình duyệt mà chừa trình duyệt khác thì vô nghĩa), Outlook (Desktop + New Outlook), Microsoft Teams (Win32 + Store app).

## 3. Điều kiện tiên quyết

### 3.1. ⚠️ Giới hạn edition Windows — đọc kỹ trước khi triển khai
| Hệ điều hành | Hỗ trợ AppLocker? |
|---|---|
| Windows Server 2012 R2 (mọi edition — Standard/Datacenter) | ✅ Có, không phụ thuộc edition |
| Windows 10/11 **Enterprise** hoặc **Education** | ✅ Có |
| Windows 10/11 **Pro** | ❌ **Không có AppLocker** — chỉ có Software Restriction Policy (SRP), yếu hơn (không phân biệt được User/Group, dễ bypass hơn) |

→ **Domain Controller (Tier 0) và Server (Tier 1)** đều dùng Windows Server → AppLocker hoạt động đầy đủ, đây là phần quan trọng nhất và triển khai được ngay 100%.
→ **Workstation (Tier 2)** — cần xác nhận edition Windows 10/11 đang dùng là **Pro hay Enterprise**. Nếu là Pro (rất phổ biến ở PC văn phòng thông thường), AppLocker sẽ **không áp dụng được** trên các máy đó khi `adm2.*` RDP vào hỗ trợ. Xem phương án dự phòng tại mục 4.5.

```powershell
# Kiểm tra nhanh edition trên 1 máy
(Get-CimInstance Win32_OperatingSystem).Caption
```

### 3.2. Checklist chuẩn bị
- [ ] Đã xác nhận edition Windows trên toàn bộ Server/Workstation liên quan (mục 3.1).
- [ ] Đã hoàn tất [[../04 - Active Directory/Tiered Administration Project/02. Phase 2 - OU Design|Phase 2]] (OU) và [[../04 - Active Directory/Tiered Administration Project/03. Phase 3 - Security Groups (AGDLP)|Phase 3]] (nhóm `GG_Tier0-Admins`/`GG_Tier1-Admins`/`GG_Tier2-Admins` đã tồn tại).
- [ ] Có 1 máy test (không phải production) để lấy thông tin Publisher của Chrome/Outlook/Teams trước khi tạo rule.

## 4. Quy trình thực hiện

### 4.1. Bật dịch vụ Application Identity (bắt buộc — AppLocker không hoạt động nếu thiếu)
AppLocker phụ thuộc dịch vụ **Application Identity (AppIDSvc)** — mặc định là *Manual*, cần chuyển sang *Automatic* qua GPO:

`Computer Configuration > Preferences > Control Panel Settings > Services` → thêm Service `Application Identity`, Startup = **Automatic**, Action = **Start**.

Hoặc qua PowerShell (dùng trong Startup Script/kiểm tra nhanh):
```powershell
Set-Service -Name AppIDSvc -StartupType Automatic
Start-Service -Name AppIDSvc
```

### 4.2. Lấy thông tin Publisher của Chrome/Outlook/Teams (bước bắt buộc trước khi tạo rule)
**Nguyên tắc quan trọng:** dùng **Publisher Rule** (dựa trên chữ ký số của file) thay vì **Path Rule** (dựa trên đường dẫn). Path Rule rất dễ bị bypass (đổi tên file `.exe`, copy sang thư mục khác) — Publisher Rule bám theo chữ ký số, đáng tin cậy hơn nhiều và tự động áp dụng cho các bản cập nhật version sau (nếu cấu hình "And higher").

Trên máy test đã cài Chrome/Outlook/Teams, chạy:
```powershell
# Chrome (per-user install: %LocalAppData%; enterprise MSI install: Program Files)
Get-AppLockerFileInformation -Path "C:\Users\<user>\AppData\Local\Google\Chrome\Application\chrome.exe" | Format-List

# Outlook (thường trong Program Files\Microsoft Office)
Get-AppLockerFileInformation -Path "C:\Program Files\Microsoft Office\root\Office16\OUTLOOK.EXE" | Format-List

# Teams (Win32 classic — nếu còn dùng bản cũ)
Get-AppLockerFileInformation -Path "C:\Users\<user>\AppData\Local\Microsoft\Teams\current\Teams.exe" | Format-List

# Microsoft Edge
Get-AppLockerFileInformation -Path "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" | Format-List
```
Kết quả trả về thông tin `Publisher`, dạng ví dụ:
```
Publisher   : O=GOOGLE LLC, L=MOUNTAIN VIEW, S=CALIFORNIA, C=US
ProductName : GOOGLE CHROME
BinaryName  : CHROME.EXE
```
Ghi lại chính xác giá trị này cho từng ứng dụng — dùng ở Bước 4.3.

### 4.3. Tạo AppLocker Policy qua GPO (khuyến nghị dùng GPMC GUI cho phần Publisher Rule — trực quan và ít lỗi hơn viết tay XML)

Tạo GPO mới: `New-GPO -Name "AppLocker-BlockOfficeInternet-AdminAccounts"`

Vào GPO → `Computer Configuration > Policies > Windows Settings > Security Settings > Application Control Policies > AppLocker`

**Bước A — Tạo Default Rules trước (bắt buộc, nếu không sẽ chặn nhầm toàn bộ Windows/PowerShell luôn của Admin):**
Chuột phải **Executable Rules** → **Create Default Rules** — tự sinh 3 rule Allow cơ bản:
- Allow Everyone: mọi file trong `%PROGRAMFILES%\*`
- Allow Everyone: mọi file trong `%WINDIR%\*`
- Allow BUILTIN\Administrators: mọi file (*)

**Bước B — Tạo Deny Rule theo Publisher cho từng ứng dụng, áp riêng cho nhóm Tier Admin:**

Chuột phải **Executable Rules** → **Create New Rule**:
1. Permission: **Deny**
2. User or group: **GG_Tier0-Admins** (lặp lại toàn bộ quy trình 3 lần cho `GG_Tier1-Admins`, `GG_Tier2-Admins`, hoặc gộp cả 3 vào 1 group tổng `GG_All-Tier-Admins` để đỡ lặp — xem gợi ý tối ưu ở mục 4.4)
3. Conditions: **Publisher**
4. Browse tới file `chrome.exe`, kéo thanh trượt lên mức **"Publisher"** (không xuống mức Product Name/File Version, để rule áp dụng cho mọi phiên bản Chrome trong tương lai)
5. Lặp lại cho: `msedge.exe`, `firefox.exe`, `OUTLOOK.EXE`, `Teams.exe`

**Bước C — Với Teams bản mới (MSIX/Store app) — cần thêm Packaged App Rule riêng:**
Chuột phải **Packaged app Rules** → **Create New Rule** → Permission = Deny → User/group = nhóm Tier Admin → Conditions = **Publisher**, chọn gói `MSTeams` đã cài trên máy test (Package Family Name dạng `MSTeams_8wekyb3d8bbwe`).

### 4.4. Tối ưu — gộp 3 nhóm Tier Admin thành 1 nhóm chung cho AppLocker (giảm số rule phải tạo)
Thay vì tạo lặp lại rule 3 lần cho từng Tier, tạo thêm 1 Global Group tổng hợp chỉ dùng riêng cho mục đích AppLocker:
```powershell
New-ADGroup -Name "GG_All-Tier-Admins" -GroupScope Global -Path "OU=Groups,DC=company,DC=local" `
  -Description "Nhom tong hop adm0/adm1/adm2 - chi dung de ap AppLocker Deny Rule"

Add-ADGroupMember -Identity "GG_All-Tier-Admins" -Members `
  (Get-ADGroupMember -Identity "GG_Tier0-Admins"),
  (Get-ADGroupMember -Identity "GG_Tier1-Admins"),
  (Get-ADGroupMember -Identity "GG_Tier2-Admins")
```
Từ đó chỉ cần tạo **1 lần** mỗi Deny Rule, áp cho `GG_All-Tier-Admins` — khi thêm/gỡ admin mới, chỉ cần quản lý thành viên của nhóm này, không cần sửa lại AppLocker Rule.

### 4.5. Phương án dự phòng cho Workstation Windows 10/11 Pro (không có AppLocker)
Nếu Tier 2 Workstation dùng bản Pro (không hỗ trợ AppLocker — xem mục 3.1):
| Phương án | Ghi chú |
|---|---|
| **Software Restriction Policy (SRP)** | Có sẵn trên Pro, cấu hình tại `Computer Configuration > Windows Settings > Security Settings > Software Restriction Policies`. Yếu hơn AppLocker (không lọc theo User/Group trong cùng 1 rule — phải kết hợp Group Policy Security Filtering ở cấp GPO để giới hạn phạm vi áp dụng theo nhóm) |
| **Nâng cấp lên Windows 11 Enterprise** | Giải pháp triệt để nhất, thường đã có sẵn qua gói Microsoft 365 E3/E5 nếu công ty đang dùng — kiểm tra lại license hiện có trước khi mua thêm |
| **Kiểm soát bằng quy trình thay vì kỹ thuật** | Với Workstation Pro chưa nâng cấp được ngay: dựa vào Phase 9 Auditing + PowerShell Logging để phát hiện hành vi bất thường sau, thay vì chặn trước — chấp nhận đây là khoảng trống tạm thời, có kế hoạch khắc phục |

### 4.6. Thiết lập chế độ Audit trước khi Enforce (bắt buộc — không bỏ qua bước này)
`AppLocker Properties` → tab **Enforcement** → đặt Executable Rules và Packaged app Rules ở chế độ **"Audit only"** trước, **KHÔNG** chọn "Enforce rules" ngay từ đầu.

## 5. Kiểm tra sau triển khai

### Giai đoạn Audit (tối thiểu 5-7 ngày làm việc)
```powershell
# Xem log Audit trên máy test — Event Viewer
# Applications and Services Logs > Microsoft > Windows > AppLocker > EXE and DLL
Get-WinEvent -LogName "Microsoft-Windows-AppLocker/EXE and DLL" | Where-Object {$_.Id -eq 8003} | Select TimeCreated, Message
```
- [ ] Rà soát log Audit, xác nhận **không** có false positive (chặn nhầm ứng dụng công việc hợp lệ mà Admin thực sự cần, ví dụ 1 công cụ quản trị nội bộ tự phát triển).
- [ ] Xác nhận Chrome/Outlook/Teams bị ghi nhận "sẽ bị chặn" đúng như log Audit khi Admin thử mở.

### Giai đoạn Enforce
Đổi Enforcement mode sang **"Enforce rules"**, test trực tiếp:
```powershell
gpupdate /force
```
- [ ] Đăng nhập bằng `adm2.nva`, thử mở Chrome/Outlook → phải bị chặn, hiện thông báo "This app has been blocked by your system administrator".
- [ ] Đăng nhập cùng máy bằng tài khoản User thường (`nva`) → Chrome/Outlook vẫn mở bình thường (xác nhận rule chỉ áp cho nhóm Admin, không ảnh hưởng User).
- [ ] Admin vẫn mở được PowerShell, ADUC, DNS Manager, RDP bình thường (không bị AppLocker chặn nhầm — vì các công cụ này nằm trong `%WINDIR%`/`%PROGRAMFILES%` đã Allow ở Default Rules).

## 6. Rollback (nếu có)
```powershell
# Gỡ tạm Link GPO nếu phát hiện chặn nhầm công cụ quan trọng
Set-GPLink -Name "AppLocker-BlockOfficeInternet-AdminAccounts" -Target "OU=Tier1-AppServers,DC=company,DC=local" -LinkEnabled No
```
Không tắt hẳn AppIDSvc hay xóa GPO — chỉ gỡ Link tạm, sửa lại rule (thường do publisher rule quá hẹp/quá rộng), test lại trên máy pilot trước khi bật lại.

## 7. Kiểm tra bảo mật
- [ ] Deny Rule luôn **ưu tiên tuyệt đối** hơn Allow Rule trong AppLocker (không cần sắp thứ tự như GPO thường) — nhưng vẫn phải xác nhận rule Deny thực sự match đúng Publisher, không bị đánh máy sai khiến rule vô hiệu.
- [ ] Rà soát định kỳ (theo lịch [[../16 - Checklists/03. Monthly Checklist]]): nhóm `GG_All-Tier-Admins` không có thành viên dư thừa — mọi thành viên trong nhóm này đều bị áp Deny Rule, đảm bảo danh sách luôn khớp với [[../04 - Active Directory/03. Administrative Accounts Register]].
- [ ] Không tạo Allow Rule "ngoại lệ" cho riêng 1 cá nhân Admin nào — nếu có nhu cầu đặc biệt thực sự chính đáng, dùng tài khoản User thường của chính họ để xử lý, không mở khóa AppLocker cho tài khoản Admin.

## 8. Troubleshooting
| Sự cố | Nguyên nhân | Cách xử lý |
|---|---|---|
| Rule không có tác dụng gì cả, Admin vẫn mở được Chrome | Dịch vụ AppIDSvc chưa chạy | Kiểm tra `Get-Service AppIDSvc`, đảm bảo Automatic + Running (mục 4.1) |
| Rule chặn luôn cả PowerShell/công cụ quản trị của Admin | Thiếu Default Rules (Bước A mục 4.3), hoặc quên chọn "Create Default Rules" | Tạo lại Default Rules trước khi thêm Deny Rule |
| Chặn được Chrome bản cài Enterprise (Program Files) nhưng không chặn được Chrome per-user (AppData) | Rule Publisher đúng thì chặn được cả 2 vị trí cài (Publisher rule không phụ thuộc đường dẫn) — nếu vẫn lọt, kiểm tra lại có tạo nhầm Path Rule thay vì Publisher Rule | Xóa Path Rule, tạo lại đúng theo Publisher (mục 4.2-4.3) |
| User thường (không phải Admin) cũng bị chặn nhầm | Gán sai User/Group khi tạo rule (chọn nhầm `Domain Users` thay vì `GG_All-Tier-Admins`) | Sửa lại Conditions của rule, xác nhận đúng nhóm target |
| Không chặn được trên Workstation dù đã cấu hình đúng | Máy dùng Windows 10/11 **Pro**, không hỗ trợ AppLocker | Xem phương án dự phòng tại mục 4.5 |
