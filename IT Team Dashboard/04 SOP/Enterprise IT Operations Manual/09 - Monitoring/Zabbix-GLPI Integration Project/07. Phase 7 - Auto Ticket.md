# Phase 7 — Auto Ticket (Zabbix → GLPI)

Liên quan: [[06. Phase 6 - GLPI API]] · [[../../07 - Helpdesk/Business Rules|GLPI Deployment Manual - Business Rules]]

## 1. Mục đích
Tự động tạo Ticket GLPI ngay khi Zabbix phát hiện sự cố nghiêm trọng — loại bỏ độ trễ con người phát hiện thủ công, đồng thời tự động đóng/ghi chú Ticket khi sự cố đã hết (Problem Resolved).

## 2. Phạm vi áp dụng
Trigger mức **Average trở lên** (theo bảng ánh xạ ở Phase 5) — **không** tạo ticket cho mức Warning/Information để tránh làm loãng GLPI.

## 3. Điều kiện tiên quyết
- [ ] Phase 5 (Trigger) và Phase 6 (GLPI API) hoàn tất.
- [ ] Đã có Category "Giám sát hệ thống" (Monitoring) trong GLPI (`Setup > Dropdowns > ITIL Categories`) để phân loại riêng ticket tự động, dễ lọc báo cáo.

## 4. Quy trình thực hiện

### Bước 1 — Tạo Webhook Media Type trong Zabbix
`Alerts > Media types > Create media type`:
- Type: **Webhook**
- Name: `GLPI Auto Ticket`

### Bước 2 — Script Webhook (JavaScript — Zabbix Webhook dùng engine JS nội bộ)
```javascript
try {
    var params = JSON.parse(value);
    var glpi_url = "https://glpi.company.local/apirest.php";
    var app_token = "APP_TOKEN_TU_PHASE_6";
    var user_token = "USER_TOKEN_SVC_ZABBIX_GLPI";

    // 1. Khởi tạo session
    var req = new HttpRequest();
    req.addHeader("Authorization: user_token " + user_token);
    req.addHeader("App-Token: " + app_token);
    var session = JSON.parse(req.get(glpi_url + "/initSession"));
    var session_token = session.session_token;

    // 2. Map Zabbix severity -> GLPI Priority (1=Rat thap ... 6=Rat cao theo thang GLPI)
    var severityMap = {
        "Disaster": 6, "High": 5, "Average": 4, "Warning": 3, "Information": 2
    };
    var priority = severityMap[params.severity] || 3;

    // 3. Tạo Ticket
    var req2 = new HttpRequest();
    req2.addHeader("Session-Token: " + session_token);
    req2.addHeader("App-Token: " + app_token);
    req2.addHeader("Content-Type: application/json");

    var payload = {
        input: {
            name: "[Zabbix] " + params.event_name,
            content: "Host: " + params.host + "\nTrigger: " + params.trigger_name +
                     "\nSeverity: " + params.severity + "\nThoi gian: " + params.event_time,
            itilcategories_id: 5,   // ID category "Giam sat he thong" - dieu chinh theo GLPI thuc te
            priority: priority,
            urgency: priority
        }
    };
    var result = req2.post(glpi_url + "/Ticket", JSON.stringify(payload));
    return result;
} catch (error) {
    Zabbix.log(4, "GLPI Webhook error: " + error);
    throw "GLPI ticket creation failed: " + error;
}
```

### Bước 3 — Tham số truyền vào Webhook (Zabbix Macro)
| Tên tham số | Giá trị Macro Zabbix |
|---|---|
| `event_name` | `{EVENT.NAME}` |
| `host` | `{HOST.NAME}` |
| `trigger_name` | `{TRIGGER.NAME}` |
| `severity` | `{EVENT.SEVERITY}` |
| `event_time` | `{EVENT.DATE} {EVENT.TIME}` |

### Bước 4 — Tạo Trigger Action gọi Webhook
`Alerts > Actions > Trigger actions > Create action`:
- Condition: Severity ≥ Average
- Operation: gửi tới Media type `GLPI Auto Ticket`

### Bước 5 — Tránh tạo Ticket trùng lặp (quan trọng)
Bổ sung logic kiểm tra trước khi tạo: search Ticket đang mở (`status != closed`) có cùng `name` chứa tên Host + Trigger trong 24h gần nhất qua `GET /Ticket?searchText[name]=...` — nếu đã tồn tại, chỉ thêm **Followup** (ghi chú) vào Ticket cũ thay vì tạo mới. Đây là bước nên bổ sung sau khi phiên bản cơ bản ở Bước 2 chạy ổn định.

### Bước 6 — Tự động đóng/ghi chú khi Problem Resolved (tùy chọn)
Tạo thêm 1 Trigger Action riêng cho sự kiện "Problem resolved", gọi Webhook tương tự nhưng gọi `POST /Ticket/{id}/ITILFollowup` để ghi "Sự cố đã tự phục hồi" thay vì đóng hẳn ticket (đóng ticket nên do con người xác nhận, tự động chỉ nên ghi chú).

## 5. Kiểm tra sau triển khai
- [ ] Giả lập 1 Trigger mức Average → Ticket GLPI xuất hiện trong vòng 1-2 phút, đúng Category/Priority.
- [ ] Test lặp lại cùng sự cố → không tạo Ticket trùng (nếu đã làm Bước 5), chỉ thêm Followup.

## 6. Rollback (nếu có)
Vô hiệu hóa Trigger Action tạm thời nếu Webhook gây lỗi/spam ticket, không cần xóa cấu hình.

## 7. Kiểm tra bảo mật
- [ ] Token nhúng trong Webhook script chỉ Super Admin Zabbix xem được (`Alerts > Media types` giới hạn quyền xem cấu hình).

## 8. Troubleshooting
| Sự cố | Nguyên nhân | Cách xử lý |
|---|---|---|
| Webhook chạy nhưng không thấy Ticket | `itilcategories_id` không tồn tại trong GLPI | Kiểm tra lại đúng ID category thật, không hardcode số bừa |
| Ticket tạo hàng loạt trùng lặp | Chưa làm Bước 5 (check trùng) | Bổ sung logic search trước khi tạo |
| Lỗi "session_token invalid" | Session hết hạn giữa các lần gọi | Đảm bảo `initSession` và tạo Ticket nằm trong cùng 1 lần thực thi script (không tách session) |
